# 后续功能迁移开发计划

更新：2026-11-14。状态：**主要功能已落地**（P1–P3 + §7 的手动导出、最近修改），P4 独立备忘及其兼容逻辑已按用户要求移除，§7 其余四项未触发。订阅的日期窗口目前仅按续费日筛选，到期日可保存和读取。参考同级 AssetMesh 项目，按个人 DSH 插件的实际用途重新取舍。

进度：`user_version` 现为 7，11 个工具（10 个功能工具 + `media_log_changes`），120 项测试。§7 两项的落地方式见该节表格；改动日志和导出脚本的行为边界见 README。源码完成情况与 desktop 实际安装情况分别核对。

**订阅和软件导入器暂未实现。**原调研记录中，本机两个 AssetMesh 库的 service_records 各 0/3 条，且那 3 条全是 `service.local`（只有 project_dir/start_command，没有金额、续费日、套餐、计费周期）；software_records 都是 0 条。按"不强行导入本地服务启动命令""不以迁移整个 AssetMesh 为门槛"的约定，等有实际来源数据时再补。

**共用工具输出：**三个模块的错误分支、unchanged 回执、输出契约共用 `src/toolkit.js`。`media_log_mark` 支持按标题直接修改；订阅和软件的名字不是唯一键，更新按 UUID，`_list` 返回 revision，所以是 `_list` → `_mark` 两次。

## 1. 目标与当前实现

目标是让用户在 DSH 中用一句话记录、查找和修改自己的资料，优先解决“记下后找不到”“记录错了不好改”“不知道哪些订阅快到期”等日常问题。每次交付一个能用的小功能，继续沿用 Node + SQLite。

当前已具备：

- 电影、剧集、动画、游戏的记录、搜索、详情和列表筛选；五种状态均可写，支持按标题直接修改、字段纠正/清空、归档/恢复。UUID 修改带 revision。
- 订阅、软件用途清单均有 mark/list/get；三个业务模块共用一个 SQLite 连接与写入开关。
- 最近改动保留 500 条摘要；提供手动 JSON 导出，输出文件不覆盖，stdout 可直接接管道。
- AssetMesh 导入器当前只搬媒体字段，不搬软件、订阅、Info、标签、关系和活动历史。
- 当前只有 Host 工具，没有插件专属的列表管理页面。
- 规划时已导入的真实库约 788 条（planned 218、有完成日期 487、632 条共用同一 `updated_at`）。本计划里“个人使用”的各项取舍以这个规模为依据；这不是实时库统计。

后续计划不改变已有媒体 ID、工具名和数据库位置。AssetMesh 提供业务规则与数据格式参考，不作为运行依赖；不要求重新编译、运行或安装旧应用。

## 2. 按价值排序

| 顺序 | 用户得到什么 | 为什么值得做 | 本轮边界 |
| --- | --- | --- | --- |
| P1 媒体闭环 | 查正在看/想看/已完成，纠正记录，归档后找回 | 直接改善已有资料库，基本都能使用现有字段 | 分 P1.1–P1.5 小步交付 |
| P2 订阅记录 | 记价格、续费/到期日期，随时问哪些快到期 | 新增功能中优先验证的方向，手机对话录入很自然 | 手动记录与按需查询 |
| P3 软件用途清单 | 记住装过什么、为什么装、哪个工具解决过某问题 | 找回个人经验，比维护安装器更有价值 | 手动清单，不自动扫描或安装 |

下文保留各阶段的目标和验收要求；当前主要功能已实现。今后的新增项仍应先用实际提问确认需求，无需另建统计或需求管理系统。

## 3. P1：把现有媒体记录用顺手

参考：[AssetMesh 媒体规则](../../AssetMesh/docs/08-media-records-v1.md)。沿用有用的字段和状态，不照搬通用资产内核。

### P1.1 列表与筛选——首个开发切片

用户可以说：“我现在在玩什么？”“列出想看的电影”“今年保存了完成日期的电影有哪些？”

交付：新增 `media_log_list`，无需片名即可查询。首版参数为 `mediaType?`、`status?`、`lifecycle?`、`completedFrom?`、`completedBefore?`、`limit?`、`offset?`；日期范围含起点、不含终点。`lifecycle` 取 `active`（默认）/ `archived` / `all`。默认按最近更新排序，**必须**用 ID 打破同时间排序的并列——导入数据里大量记录共用同一 `updated_at`，没有 tiebreak，分页顺序实际不确定。

- 返回名称、类型、年份、状态、评分、进度和可继续操作的 `assetId`；短评正文继续通过 get 按需读取。
- 评分和进度用新的 `mapListItem` 映射，**不要扩 `mapCandidate`**——它同时喂 search 结果和 `TARGET_CONFLICT` 的 candidates，形状一变，错误渲染和 search 展示都要跟着改。
- 分页延续现有 `items/offset/limit/total` 约定；未穷尽时 `total=null`。空页说明“本页为空”，不会把越界分页说成整个库没有匹配。
- 相对日期由模型转换成明确的带时区起止时间。
- 完成日期范围用 `julianday(completed_at)` 比较，**不用文本比较**：导入的日期是 `2025-07-09T00:00:00+00:00`，插件新写的是 `2025-07-09T00:00:00.000Z`，同一时刻文本序不同，边界上会和“含起点、不含终点”相反。`julianday()` 两种写法和非 UTC 偏移都吃，`NULL` 返回 `NULL`，正好实现下一条。代价是不能走索引、全表扫描——个人库规模下这是有意的取舍，不为它建索引。
- 完成日期为空的条目不计入日期范围；不从评分、导入时间或更新时间猜测看完时间。此查询不能回答重看次数。无法解析的日期同样落不到范围里（`julianday()` 对非法文本返回 NULL），这是有意的静默，不额外报错。
- 渲染要读起来像回答，不像检索报告：“在玩的有 2 个：《艾尔登法环》（游戏，进度 3/50 小时）……”，不要“找到 N 条候选”。

验收：

- 混合类型、状态的临时库中，“在玩什么”只返回对应 active 游戏，评分和进度能出现在模型最终看到的内容中。
- 多页查询排序稳定；越过末页后仍正确说明分页结果。
- 有完成日期、无完成日期、`+00:00` 与 `.000Z` 混写的记录能正确进入或排除日期范围，尤其是边界瞬间。
- 查询前后原记录与 revision 一致；测试同时检查 execute 的值和真实 render 的内容。

实现位置：`src/media.js` 增加列表参数校验，`src/tools.js` 增加查询与展示，`test/tools.test.js` 增加以上场景。复用现有数据库和语句缓存，本切片不改表、不增加前端构建。

### P1.2 完整状态

用户可以说：“把这部电影放进想看”“这部剧先搁置”“这个游戏弃了”。

交付：让 mark 支持已有的 `planned / in_progress / completed / paused / dropped`，列表可以筛选对应状态。新建想看条目不必伪装成正在看。**新建不再强制 `status`，缺省 `planned`**——“记一下《沙丘2》”现在会直接 `INVALID_ARGUMENT`，模型只能替你编一个状态；缺省“想看”是唯一自然的解释。

验收：五种状态均能新建/修改并正确展示；直接纠正状态不受多余流程限制；同值重提不增加 revision。

日期规则逐条定死（这是对 [AssetMesh 媒体规则](../../AssetMesh/docs/08-media-records-v1.md) 的显式偏离，实现时不要顺带照搬）：

| 变化 | 本插件 | AssetMesh（不采用） |
| --- | --- | --- |
| 进入 `in_progress` | `started_at` 为空时补上 | 同 |
| 进入 `completed` | 只补 `completed_at` | 两个都补 |
| 进入 `paused` / `dropped` | 两个日期都不动 | — |
| 离开 `completed` 去别处 | `completed_at` 保留 | 清空 `completed_at` |
| 回到 `planned` | 两个日期都保留 | 清空 `started_at` |

只补状态自己那个日期，和 P1.1”不从评分、导入时间或更新时间猜测看完时间”是同一条原则：**”什么时候开始看的”没法从”看完了”推出来，缺着比造假好。**保留则是为了不毁掉导入进来的历史日期。不改状态、只改评分/进度/短评时，两个日期都不动。

### P1.3 纠正与清空

用户可以说：“片名改成《沙丘：第二部》”“年份填错了，改成 2024”“清空这条短评”。

交付：在现有 mark 更新模式中增加 `metadata: {title?, mediaType?, year?}`，并用 `clear: ['rating'|'year'|'notes'|'progress']` 表达清空。create 仍使用现有 target 结构；`metadata` 和 `clear` 只用于 update。

- 省略字段保留，`clear` 里的字段置空；标题和类型不接受清空（schema 是 NOT NULL）。
- **清空不用 `null` 传值，用显式的 `clear` 数组**：`defineTool` 在 execute 之前就按声明的 JSON schema 校验参数，而 `type: ['string','null']`、`enum` 里混 `null` 都会让工具构建直接失败，`type:'object'` 也不接受 null——`null` 约定只能靠 `oneOf` 硬绕。显式数组对模型更可靠，也和现有 `replaceNotes` 的风格一致。
- 清空进度作为整体操作处理，避免留下只有单位的无效进度（schema 有这条 CHECK）。
- 用户明确要求替换/清空短评时，沿用 `replaceNotes` 表达意图；不增加新的确认令牌或逐字段审批。
- **改名/改类型前查一次同名冲突**：复用 `classifyCandidates`，排除自身 id。命中就返回 `TARGET_CONFLICT` + candidates——否则把 A 改成 B 的确切标题会造出同名重复，之后新建永远撞冲突、`classifyCandidates` 永远 ambiguous。
- 按 UUID 纠正指定记录，其他同名记录保持原样。新增同名作品的支持另按实际需求补，不扩进本切片。

验收：能改对目标条目，未提供的字段保持原值；旧 revision 仍被拒绝；**重试同值得到 unchanged**（`patchIsNoop` 必须补上 title/mediaType/year/lifecycle，现在它不知道这几个字段）；现有新建调用保持兼容。

### P1.4 归档与恢复

用户可以说：“把这条重复录入先归档”“恢复刚归档的记录”。

交付：mark 更新模式增加 `lifecycle: active | archived`，复用现有字段和 revision。默认列表隐藏归档项；search 保持能搜到归档记录，并清楚标记；恢复后原 ID、评分、进度和短评仍在。

- 归档时写 `archived_at`，恢复时清空——schema 里本来就有这一列，不清会让恢复后的记录挂着归档时间进备份和导出。
- `patchIsNoop` 要把 lifecycle 算进去，否则重复归档会涨 revision，直接违反下面那条验收。
- 已知边界（写进 README 就好，不用改代码）：`classifyCandidates` 对“仅归档的同名”也返回 ambiguous 挡住新建，所以归档一条重复录入之后**仍然不能重建同名条目**。用户很可能预期“归档了就能重新录”。

验收：归档/恢复可往返，重复提交不改 revision；不误改观看状态。此阶段不增加永久删除和自动合并。

### P1.5 按标题直接改——单次调用完成修改

用户可以说：“把《沙丘2》标成看完”“《艾尔登法环》打到 9 分”。

交付：mark 的 update 接受 `target: {title}`，工具自己在写事务里用 `classifyCandidates` 定位：唯一 active 确切同名就直接改，多个就返回 candidates 让用户选，没有确切同名就返回最接近的候选。`target: {title, mediaType}` 仍表示新建；类型纠正放在 `metadata.mediaType`。按 UUID 的更新保持原样，`expectedRevision` 不动。

- 这把最常见的操作从 3 次调用（search → get → mark）压到 1 次，是个人使用里收益最大的一条。
- 读取和写在同一个事务里，所以这条路**不可能** `STALE_REVISION`——比现在的流程还稳，不需要额外处理。
- 与 P1.3 / P1.4 没有依赖，想提前做可以单独插队。

验收：“标成看完”“打分”“归档”三类指令都能一次调用完成；歧义时列出可操作的 assetId 而不是瞎猜；短评替换仍走 `replaceNotes` 确认。

## 4. P2：订阅记录与到期查询

参考：[AssetMesh 订阅语义](../../AssetMesh/docs/10-services-subscriptions-v1.md)。只取个人记账需要的部分。

实际提问：“记一下某服务每月 20 美元，下次续费是 12 月 10 日”“未来 30 天哪些快到期？”“这个订阅取消自动续费了”。

最小交付：

- 独立 `subscriptions` 表：名称、提供方/套餐（可选）、金额、币种、计费周期、下次续费日期、到期日期、是否自动续费、备注、归档标记、revision 和创建/更新时间。
- `subscription_mark / subscription_list / subscription_get`：创建/局部修改、查询与详情。无需先构造服务、账户、发票等对象。
- 金额按整数小单位保存；首版先按 CNY/USD 设计，实际记录需要其他币种时补相应单位规则，按币种分别汇总。支持月付、年付和按量付费；未知金额留空，不把它算成 0。
- 同币种固定月付/年付记录可给出月均估算；按量付费、未知费用单列。此估算是本插件的拟新增便利查询，不宣称旧 AssetMesh 已实现完整费用报表。
- 续费与到期分开：取消自动续费后，已支付的有效期仍可保留。日期过去只说明已过登记日期，不推断已扣款或服务已失效。
- “续费了”先记录用户给出的事实和新日期；不擅自按旧日期顺延。用户需要完整缴费流水时再单独扩展历史。

验收：能完成“登记 → 列出临近日期 → 纠正金额/日期 → 取消自动续费 → 归档”的闭环；金额修改和普通日期修改无需重复确认；查询不会凭空生成新续费日期；不同币种及未知金额展示正确。

迁移：在媒体导入器之外按需增加订阅导入，只提取旧 Service 中真正有订阅意义的记录。保留旧 ID 和备注，已存在的目标记录不被旧数据覆盖；不强行导入本地服务启动命令、运行状态或全部 Service 字段。来源不明确的条目先列出供选择。

## 5. P3：软件用途清单

参考：[AssetMesh 的 purpose 语义](../../AssetMesh/docs/09-software-inventory-v1.md)。首版重点是用户的“为什么装”，不复刻软件发现系统。

实际提问：“记一下这个 PDF 工具用来压缩文件”“以前处理字幕用的是什么？”“这个工具不再用了，但留着用途记录”。

最小交付：

- 独立 `software` 表：名称、类别、用途、官网/来源链接、可选版本与平台、备注、使用/停用状态、revision。
- `software_mark / software_list / software_get`，按名称和用途检索，支持局部纠正和停用后找回。
- 查询只表达已登记的情况，不把“在清单中”说成“当前机器已安装/正在运行”。
- 从旧软件记录按需搬名称、用途、备注、版本和必要链接；手动维护的用途不被外部信息覆盖。

验收：按“字幕”“PDF”等用途能找回相关软件；版本变化不会丢失用途；停用不删除备注；不扫描、不安装、不卸载本机软件。

## 8. 保持插件轻量的实施约定

- 新模块使用独立表和模块文件，共用现有 SQLite 连接与事务。现有文件还便于维护时就继续使用，不预建 Repository、通用资产内核、插件框架或多层转发。
- 工具维持 `{ok,data}` / `{ok,error}`，保留现有 writeEnabled、revision 和明确的短评替换规则；常规记录、修改、归档不新增审批流程。
- 只有真正需要改表时才补对应版本的事务 SQL，并沿用 `user_version`。当前保留的表不需要列级迁移，新增表由 `CREATE TABLE IF NOT EXISTS` 创建，不预留空迁移框架。
- **已有表加列之前必须先写增量迁移**：`CREATE TABLE IF NOT EXISTS` 对已存在的旧表静默 no-op，缺列会在 prepare 阶段抛错——那是插件 bug（isError），不是干净的 `fail` 值。加新表没这个风险。迁移必须在版本号提升**之前**执行，否则崩在中间会把库标成最新却缺列。
- 每个切片完成时同步“会骗人”的那几句文档：README 的工具表、错误码清单和「当前版本的能力边界」段。负载模型契约的是工具 description，README 只改会骗人的部分，不做全文同步。
- 导入按模块附带：先用临时源/目标库验证，再按明确指定的来源运行；不以“迁移整个 AssetMesh”作为任何阶段的门槛。
- 测试抓住真正的用户闭环：临时 SQLite、字段保留与修改、真实工具输出及模型最终可见内容；不为每个函数、文案或假想环境补一套防御测试。通过后不反复扩测同一范围。
- 验收只用临时库；正式 `~/.dsh/media-log/media.db` 的写入、真实导入和 desktop 安装更新按用户另行明确的操作范围执行。

原生灵动岛、CPU/配额采样、本地服务进程管理、通用图谱/自动合并、云同步、多用户权限不迁入这轮插件开发。若将来确有需要，分别评估独立扩展；它们的维护成本不应成为个人资料记录的默认负担。
