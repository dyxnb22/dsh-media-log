## 2. 实施约定

- 继续小切片交付，每片能用。新模块用独立表和模块文件，共用现有 SQLite 连接与事务；
  不预建 Repository、通用资产内核、插件框架或多层转发。
- **不改变已有媒体 ID、工具名和数据库位置。**
- 工具维持 `{ok,data}` / `{ok,error}`，保留 writeEnabled、revision 和短评替换规则；
  常规记录、修改、归档不新增审批流程。
- 只有真正需要改表时才补对应版本的事务 SQL，沿用 `user_version`；新增表用
  `CREATE TABLE IF NOT EXISTS`。**已有表加列必须先写增量迁移、再提升版本号**——
  `CREATE TABLE IF NOT EXISTS` 对旧表静默 no-op，缺列会在 prepare 阶段抛错成插件 bug
  （isError）而不是干净的 `fail`；迁移若落在版本号提升之后，崩在中间会把库标成最新却缺列。
- 日期范围比较用 `julianday()` 不用文本比较：导入的 `+00:00` 和新写的 `.000Z` 是同一时刻
  的不同文本序，边界上会和「含起点不含终点」相反；`julianday()` 对非法文本返回 NULL，
  有意静默。代价是全表扫描，个人库规模下有意为之，不为它建索引。
- 列表分页按最近更新排序时**必须用 ID 打破并列**——导入数据里大量记录共用同一 `updated_at`，
  没有 tiebreak 分页顺序实际不确定。
- 列表条目用独立的 `mapListItem` 映射，**不扩 `mapCandidate`**——它同时喂 search 结果和
  `TARGET_CONFLICT` 的 candidates，形状一变，错误渲染和 search 展示都要跟着改。
- `patchIsNoop` 每接受一个新可更新字段就要把它算进去，否则同值重提会涨 revision。
- 清空字段不用 `null` 传值，用显式的 `clear` 数组——`defineTool` 的 schema 不接受
  `type: ['string','null']`，`enum` 混 `null` 会让工具构建直接失败。
- 渲染读起来像回答，不像检索报告：「在玩的有 2 个：《艾尔登法环》……」，
  不是「找到 N 条候选」。
- 每个切片完成时同步 README 会骗人的那几句：工具表、错误码清单和「当前版本的能力边界」段。
  负载模型契约的是工具 description，README 只改会骗人的部分，不做全文同步。
- 导入按模块附带：先用临时源/目标库验证，再按明确指定的来源运行；不以「迁移整个
  AssetMesh」作为任何阶段的门槛。
- 测试抓真正的用户闭环：临时 SQLite、字段保留与修改、真实 execute → render 及模型最终
  可见内容；不为每个函数、文案或假想环境补防御测试，通过后不反复扩测同一范围。验收只用
  临时库——正式 `~/.dsh/media-log/media.db` 的写入、真实导入和 desktop 安装更新按用户
  另行明确的操作范围执行。

2. `media_log_changes` 的摘要粒度是否够用。
3. 标签/关联的触发场景是否真出现。
